# yolo-touchdesigner interface reconnaissance

Upstream inspected: `external/yolo-touchdesigner` at commit
`b5ab8ad2641b51670e8117c9e6e2b4e5745a3521`.

This document records the local source interface only.  The component package
(`release/yolo.tox`) is a TouchDesigner binary format, so connector positions,
parameter-page labels, and final operator promotion still need a live-project
check.

## Result path

### VERIFIED FROM SOURCE

The component sends frames to its local browser-hosted YOLO runtime over a
WebSocket.  `td_scripts/upload_frames.py` reads the internal `source` TOP with
`numpyArray(delayed=True)`, packs it as 8-bit CHW RGB, and sends a versioned
binary packet to `yolo_server/webserver1`.  The browser runtime performs the
inference and sends JSON results back over that WebSocket.

`td_scripts/webserver1_callbacks.py` writes received JSON result text directly
to the internal `predictions` DAT.  Its dense binary results are copied into
the sibling `segmentation_data` and `depth_data` TOPs.  This establishes these
named component-facing data sources:

| Data | Source-backed operator | Data form |
| --- | --- | --- |
| Detection / pose results | `predictions` | JSON text in a DAT |
| Segmentation image | `segmentation_data` | one-channel `float32`, H x W TOP buffer |
| YOLO monocular depth image | `depth_data` | one-channel `float32`, H x W TOP buffer |
| Status / synchronization | `status`, `tick` DATs | JSON/status text |
| Webcam devices | `webcam_list` DAT | JSON text |

No user-facing CHOP output is established by the inspected source.

### VERIFIED FROM TOUCHDESIGNER RUNTIME: public depth TOP

Phase 1 depth sampling uses the public YOLO Depth TOP through an explicit
user-configured reference. In the current development project it is
`/project1/yolo/depth`, but that path is an observation and must not be
hard-coded. `numpyArray()` returned `float32` data in observed shape
`(720, 1280, 4)`; the resolution is not fixed. Depth is sampled from R/channel
0. RGB appeared to contain the depth representation, alpha was 1, and observed
values exceeded 1.0 (approximately 0.555 to 1.328 in one frame).

Movement testing observed lower raw values near and higher raw values far
(roughly 0.68 near to 2.37 far). These values are relative/raw, non-metric,
and must be preserved without normalization or clamping as `depth_raw`.

The source does not prove which of these internal operators are exported as
the `.tox` component's output connectors.  A helper must therefore take an
explicit DAT/TOP reference rather than assume connector indices.

### REQUIRES TOUCHDESIGNER RUNTIME VERIFICATION

- Which DAT/TOPs are promoted or wired to the outer component outputs, and
  their output connector order.
- Whether `source` is fed by the first external TOP input and its accepted
  pixel format/resolution at the component boundary.
- The actual parameter-page labels and whether every query parameter below is
  exposed by the component UI.

## Detection JSON schema

### VERIFIED FROM SOURCE

The JavaScript runtime formats results in `src/utils/protocol.js` and sends one
of these JSON forms (`src/pipeline.js`):

```json
{
  "type": "yolo",
  "frame": 0,
  "seq": 0,
  "videoFrame": 0,
  "width": 640,
  "height": 640,
  "predictions": ["...normal detection records..."]
}
```

When both object detection and pose are enabled it uses `type:
"yolo_combined"` and contains `yolo` plus `yolo_pose` arrays.  In pose-only
mode it uses `type: "yolo_pose"` and `predictions` is the pose array.  The
combined-message field names are:

```json
{
  "frame": 0,
  "seq": 0,
  "videoFrame": 0,
  "width": 640,
  "height": 640,
  "yolo": [],
  "yolo_pose": []
}
```

Normal detection records contain exactly the following base fields:

```json
{
  "tx": 0.5,
  "ty": 0.5,
  "width": 0.2,
  "height": 0.3,
  "categoryName": [0],
  "score": 0.9,
  "id": 1
}
```

`categoryName` is populated as a one-element array containing the upstream
numeric `label`; the inspected source does not provide a class-name lookup.
For oriented-bounding-box models, records can additionally contain
`angleRadImage`, `angleRad`, `angleDeg`, and `polygon` (four normalized
`[x, y]` points).

`id` is an integer generated by the runtime's separate IoU trackers (one for
detection and one for pose).  IDs start at 1 and persist only while IoU
matching succeeds; they are not detector-supplied identity IDs.  Tracks are
removed after the configured miss TTL, and only tracks observed in the current
frame are emitted.  Preserve this ID unchanged downstream; do not create a
second identity tracker.

## Geometry and coordinates

### VERIFIED FROM SOURCE

YOLO decoding works in input-image pixels and produces internal boxes as
`[x, y, width, height]`, where `x, y` are image top-left coordinates and image
Y increases downward.  Before serializing, `mapBoxYFlipNorm()` divides X and
width by image width, divides height by image height, and flips Y:

`[x/W, (H - (y + height))/H, width/W, height/H]`.

Thus the serialized coordinates are normalized to 0..1 and use a bottom-left
origin.  Normal object detections then convert that normalized lower-left box
to a center point: `tx = x + width/2`, `ty = y + height/2`.  So for a normal
detection:

```text
x1 = tx - width/2;  y1 = ty - height/2
x2 = tx + width/2;  y2 = ty + height/2
```

The top-level `width` and `height` fields report the inference frame size;
they default to 640 x 640 in the browser runtime.

### Pose data

#### VERIFIED FROM SOURCE

Each pose record has the normal base fields plus:

```json
"keypoints": [{"x": 0.5, "y": 0.5, "score": 0.9}]
```

Keypoints are normalized and Y-flipped with the same bottom-left coordinate
convention.  The code supports a model-provided count of `(channels - 6) / 3`
(the bundled YOLO26 pose decoder describes 17 points).  Unlike normal
detections, pose serialization assigns `tx` and `ty` directly from the
normalized lower-left box, not its center.  An adapter must handle that
intentional schema difference rather than treat pose `tx`/`ty` as centers.

### REQUIRES TOUCHDESIGNER RUNTIME VERIFICATION

- Whether the external TOP path introduces a vertical flip before the source
  code observes the image.
- The exact model-dependent class catalogue and practical keypoint count.

## Configuration and lifecycle

### VERIFIED FROM SOURCE

The browser URL configuration recognizes these relevant keys (case aliases are
also present in `src/config.js`):

| Purpose | Keys / defaults |
| --- | --- |
| Object stream and model | `Objecttrackingenabled` (true), `Objecttrackingmodel` (`yolo11n`) |
| Pose stream and model | `Posetrackingenabled` (true), `Posemodel` (`yolo11n-pose`) |
| Detection score / IoU / limit | `Detscoret` 0.4, `Detiout` 0.45, `Dettopk` 100 |
| Pose score / IoU / limit | `Posescoret` 0.35, `Poseiout` 0.45, `Posetopk` 50 |
| Detection tracker | `Detrkiou` 0.5, `Detrkttl` 2 |
| Pose tracker | `Posetrkiou` 0.5, `Posetrkttl` 2 |
| Runtime connection | `wsPort` 62309, `binary` false, `cpu` false |
| Dense streams | `Segmentationenabled`, `Segmentationmodel`; `Depthenabled`, `Depthmodel` |

The browser must initialize its ONNX sessions and establish the local
WebSocket connection before TouchDesigner can receive results.  In binary/TOP
mode the sender uses one-in-flight flow control (`busy`) and waits for a
response to clear it; absent connection/results therefore stalls new frames.
The binary protocol accepts only a 640 x 640 input packet in the inspected
browser code.  The TouchDesigner upload script likewise accepts either a
vertically packed planar 640-wide input or a 640 x 640 interleaved input.

### REQUIRES TOUCHDESIGNER RUNTIME VERIFICATION

- The user actions that launch/refresh the embedded browser and WebSocket
  server, and any required startup delay.
- Whether non-640 source TOPs are resized elsewhere in the `.tox` network
  before `upload_frames.py` runs.
- Whether the browser host/ONNX backend is available on each target
  TouchDesigner build and GPU configuration.

## Adapter implications

`yoloData` should consume the JSON DAT explicitly, parse `type` before
selecting an array, preserve `id`, use `categoryName[0]` as `class_id`, and
leave `class_name` predictably empty until a documented label map is supplied.
It must normalize normal and pose boxes separately because their serialized
`tx`/`ty` meanings differ.  It should emit canonical lower-left normalized
coordinates and derive both corners and center consistently.
